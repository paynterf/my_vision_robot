Grok:
Yes — the problem still exists in some form, and your enums.h workaround remains valid and effective.

What the issue is
This is a long-standing Visual Studio IntelliSense bug (error E0144: “a value of type X cannot be used to initialize an entity of type X”) that especially affects enums. It shows up with Visual Micro on .ino files even though the code compiles and runs fine. It is primarily a Microsoft IntelliSense parser limitation (not a pure Visual Micro bug), and it has been reported for years.

Mentions matching your timeline (around 2022–2023)
- In late 2022 there was a detailed Visual Micro forum thread about exactly this with Teensy boards. Users (including one with an AnomalyCode-style enum almost identical to yours) saw red squiggles on enum usage in .ino files. Common successful workarounds included:
  - Moving the enum to a .h file (precisely what you did).
  - Using typedef enum.
  - Declaring variables as auto.
  - Using fully qualified names (AnomalyCode::ANOMALY_STUCK_AHEAD).
- Visual Micro noted that the Arduino prototype-generation step (which happens at compile time) is not visible to IntelliSense, so enums defined in the .ino can confuse the parser. A .h file avoids that.
- Around the same period Visual Micro released a major IntelliSense upgrade (Visual Micro 2.0 / new project format) that uses a more GCC-aware engine. New projects use it automatically; older ones need migration.

Your January 2023 note about switching to enums.h to kill the VS2022 IntelliSense errors matches this exactly.

Current status (2024–2026)
The same E0144 enum error continues to be reported even after the upgraded IntelliSense system:
- Multiple 2024 Visual Micro forum threads show the identical error on simple enums in .ino files. Fixes/workarounds that still worked included switching the solution configuration from Arm64 to Arm, using fully qualified enum names, or typedef.
- Related E0144 issues are still being reported (and occasionally fixed) in newer Visual Studio versions as recently as 2025–2026.

Visual Micro’s upgraded IntelliSense (available since mid-2023) is significantly better and reduces many of these problems, but it does not completely eliminate the enum case for every project/configuration/board.

Do you still need enums.h in your current project?
Probably yes if you want zero IntelliSense noise, but you can test whether you can drop it:

1. Make sure you are on a recent Visual Micro version.
2. Check whether the project is using the new IntelliSense system — in Solution Explorer the project should show (Arduino) after its name. If not, use vMicro → Convert Solution To Latest Format.
3. Temporarily move the enum back into the .ino and see if the red squiggles return.
4. If they do, the other light workarounds (keep the enum in a .h, use typedef enum AnomalyCode { … } AnomalyCode;, or always use AnomalyCode::VALUE) still work.

Bottom line: Your January 2023 decision to use enums.h was the correct and most reliable fix at the time, and it is still a good practice today. The underlying IntelliSense limitation has not fully gone away, so you do not have to change anything if the current approach is working for you.

What's the difference between using enums.h vs typedef enum

Grok:
Both are workarounds for the same Visual Studio / Visual Micro IntelliSense bug (the E0144 “value of type X cannot be used to initialize an entity of type X” error on enums). They solve it in different ways and have different trade-offs.

1. enums.h (what you currently use)
You put a normal enum in a separate header:

// enums.h
#pragma once
enum AnomalyCode
{
  ANOMALY_NONE = 0,
  ANOMALY_STUCK_AHEAD,
  ANOMALY_STUCK_BEHIND,
  // ...
};

Then #include "enums.h" in your .ino.

Why it works
IntelliSense often struggles with types defined directly inside a .ino file (because of how Visual Micro injects Arduino prototypes and processes the sketch). Moving the type into a real .h file sidesteps that parsing problem. This has been one of the most reliable fixes reported on the Visual Micro forums for years.

Pros
- Cleanest source — the enum looks exactly like normal C++.
- Works well even with function return types, parameters, etc.
- Easy to share across multiple files.

Cons
- Extra file to maintain.
- Definitions are not right next to the code that uses them.

2. typedef enum (inline workaround)
You keep everything in the .ino but write it like this:

typedef enum AnomalyCode_t
{
  ANOMALY_NONE = 0,
  ANOMALY_STUCK_AHEAD,
  ANOMALY_STUCK_BEHIND,
  // ...
} AnomalyCode;

AnomalyCode errcode = ANOMALY_STUCK_AHEAD;   // usually no squiggle

(or the shorter form typedef enum { ... } AnomalyCode;)

Why it works
Giving the enum both a tag name and a typedef name seems to satisfy Visual Studio’s IntelliSense parser better. In the 2022 Teensy thread (and a January 2026 report) this removed most of the red squiggles even when the definition stayed in the .ino.

Pros
- Everything stays in one file.
- Often enough to silence the error without a separate header.

Cons
- Slightly more verbose / old-C style.
- Not always complete — some people still saw squiggles on functions that return the enum type.
- In pure C++ the typedef is unnecessary (you can just use enum AnomalyCode), so it feels like a hack.

Which should you use?
Approach       | Reliability for IntelliSense | Cleanliness | Recommendation
enums.h        | Excellent                    | High        | Best long-term
typedef enum   | Good (usually)               | Medium      | Fine if you prefer everything inline

Since you already have enums.h and it eliminated the errors, there is no strong reason to switch. The typedef form is mainly useful if you want to try keeping the enums inside the .ino without the red underlines. Both are still valid workarounds on current Visual Micro versions.
